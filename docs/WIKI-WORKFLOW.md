# 지식 위키 작업 흐름

이 저장소의 `wiki/` Markdown이 콘텐츠 원본이다. 출판 사이트는 이를 빌드해 정적 JSON으로 만들기 때문에 자료를 편집할 때 생성 파일을 직접 수정하지 않는다. 작업은 질문이나 개념에 필요한 출처를 좁혀 확인하고, 필요한 문서만 갱신한 뒤 인덱스와 검사를 업데이트하는 순서로 한다.

## 1. 기존 지식부터 찾기

먼저 `wiki/index.md`와 해당 분류의 `index.md`를 읽고 관련 문서를 따라간다. 질문 문서는 연결된 성경 본문, 본문 관계, 개념, 참고 자료를 출발점으로 삼는다. 이미 확인한 출처와 요약이 있으면 그대로 활용하고, 필요한 공백이 있을 때만 새 조사를 한다. 전체 위키를 다시 읽거나 모든 출처를 반복 수집하지 않는다.

## 2. 출처 수집과 확인

새 웹 자료는 수집 명령으로 참고 문서 초안을 만들 수 있다.

```bash
npm run wiki:ingest -- --url https://example.org/article --id source-slug --title "자료 제목" --related questions/acceptance,concepts/grace
```

`--related` 값은 `wiki/`에 있는 문서의 bundle-relative 경로이며 쉼표로 구분한다. 수집기는 `raw/ingest-catalog.json`에 URL, 확인 시각, 접근 상태, 해시와 관련 문서를 기록한다. 접근 가능한 원자료의 바이트는 `raw/snapshots/<sha256>`에 저장하지만, `raw/snapshots/`는 `.gitignore` 대상이어서 Git에 추가되지 않는다. 기존에 편집된 출처 조사 메타데이터는 `raw/source-catalog.json`에서 관리한다. 저작물 원문, 설교 전사, 긴 인용을 위키나 카탈로그에 옮기지 않는다.

수집은 초안 작성이지 원자료 검토를 대신하지 않는다. 원문을 직접 읽을 수 있으면 제목·저자·본문 범위를 확인하고 자신의 말로 요약한다. 페이지 개요, 카탈로그 항목, 검색 결과 일부, 원문 전체 확인은 분명히 구별한다. 접근이 막혔으면 그 상태를 그대로 기록하고, 간접 단서로 저자의 상세 주장을 만들지 않는다. 원문 전문과 검색 결과의 해시가 달라졌다면 해당 출처와 연결 문서만 재확인한다. 원문을 읽지 않은 사람을 저자나 검토자로 표시하지 않는다.

## 3. 읽을 수 있는 문서로 편집

일반 문서의 경로와 ID는 `wiki/<분류>/<slug>.md` 및 bundle-relative `분류/slug`다. 사이트 주소에서 쓰는 `public_id`는 별도 식별자이므로 파일을 옮겨도 안정적으로 유지한다. 문서에는 `type`, `title`, `description`, `public_id`, `status`, `published`, `tags`, `sources`, `generated`를 둔다. 출처마다 고유한 `sources[].id`, 원자료 `resource`, 제목을 기록하고, 생성 기록에는 실제 작업자·프로세스와 ISO 8601 시각을 쓴다. 사람 이름을 작성자나 검토자로 꾸며 쓰지 않는다.

공개 문서 본문은 한국어 prose로 작성하고, 인용 키는 같은 문서의 `sources[].id`와 일치시킨다. 문서 간 Markdown 링크는 번들 루트 기준 `/concepts/grace.md` 또는 문서 상대 경로를 사용하고, 질문 문서의 본문·경험 연결과 관계 문서의 양 끝점은 실제 공개 문서를 가리켜야 한다. 필요한 비교나 종합은 해당 질문의 본문에 근거를 밝혀 직접 작성한다. 질문 페이지가 요구하는 필수 섹션과 문서 유형별 메타데이터는 기존 동종 문서를 참고한다.

일반 Markdown·OKF 소비자는 의미가 통하는 제목과 단락, 내부 링크, YAML frontmatter를 읽으면 된다. 프로젝트의 추가 검사는 안정적인 공개 문서에 출처 ID, 유효한 사이트 링크, 학습 데이터 구조 등이 있는지 확인한다. `status: draft`와 `published: false`인 초안은 공개 사이트 번들에 실리지 않는다. `verified`는 실제 수행한 내용·출처 대조의 주체와 시각을 기록한다. 구조 검사와 내용 검토를 구별하고, 사람이 직접 검토했을 때만 `human:` 주체로 표시한다. 의미 있는 내용 수정 뒤에는 기존 검토를 로그로 옮기고 현재 개정본을 다시 검토한다.

## 4. 인덱스와 갱신 기록

문서 제목·링크·설명을 바꾼 뒤에는 다음 명령으로 위키 인덱스를 다시 만든다. 명령 뒤 문장은 날짜별 갱신 기록에 추가된다.

```bash
npm run wiki:sync -- "복음과 은혜 개념의 설명 및 연결 질문을 갱신했다."
```

`wiki/log.md`는 새 기록을 위에 쌓으므로 날짜 순서를 확인한다. 출처를 조사한 경우 기록에는 실제 읽은 범위와 관련 문서를 간단히 남긴다. 변하지 않은 자료는 다시 다운로드하거나 요약하지 않는다.

## 5. 검사 및 배포

```bash
npm run content:check
npm test
npm run build
```

`content:check`는 출판 문서의 YAML과 ID, 인용 키, 링크, 질문·본문·관계·학습 경험의 프로젝트 규칙을 검사한다. 테스트와 빌드는 앱 데이터와 사용자 흐름을 확인한다. `npm run check`는 세 검사를 묶어 실행하며 GitHub Actions도 이 검사를 통과해야 GitHub Pages에 배포한다. `src/generated/content.json`은 로컬 빌드 산출물이므로 커밋하지 않는다.

## 6. 질문에서 지식을 축적하고 위키를 점검하기

자료에 대한 질문을 받으면 인덱스에서 관련 문서를 좁혀 읽고, 원자료를 대조하면서 인용을 포함한 답을 만든다. 재사용할 만한 비교·종합을 위키에 남기도록 요청받았다면 일반 OKF 초안을 작성하고 관련 문서에 링크한다. 문서 간 다른 견해를 조용히 덮어쓰지 말고 출처와 차이를 함께 설명한다.

`npm run wiki:lint`는 공개 개념·참고자료의 들어오는 연결, `stale_after`가 있는 자료의 재확인 기한, 조사 대기 문서를 점검한다. 오래된 교리라는 이유만으로 성경 해석에 임의의 만료일을 붙이지 않는다. 연결 공백과 기한은 도구로 찾고, 모순·과도한 일반화·저자별 견해 차이는 관련 원자료를 읽어 점검한다. 필요한 수정 후 인덱스와 로그를 갱신한다.

`npm run test:browser`는 배포용 빌드를 만든 뒤 데스크톱과 모바일 Chromium에서 실제 조작을 확인한다. CI는 이미 빌드한 결과에 브라우저 검사를 수행하고, 모든 검사가 성공해야 배포한다.

## 7. 책과 함께 읽기와 설치 자료

`type: Study Series`는 기존 성경 읽기 경로와 구분한 소그룹·개인 읽기 과정이다. `books`는 공개 Reference 문서 경로 배열, `passages`는 본문 배열, `experience`는 탐색 문서를 가리킨다. 과정에는 `## 대화와 작은 실천`을 둔다. `books`도 지식 그래프의 연결과 역참조에 포함되며, 책 문서는 확인한 범위를 공개한다.

설치 자료의 선택적 `logos` 필드는 `resource_id`, `uri`, `access`를 기록한다. `LLS:RESOURCEID`에 대응하는 `logosres:resourceid`만 앱 열기 링크로 허용한다. 이 필드는 원자료의 HTTP(S) 출처를 대체하지 않는다. 로컬 책의 서지 확인, 공개 샘플 읽기, 특정 본문 읽기는 각각 별도로 기록한다.

## 8. 7일 읽기 안내

`type: Reading Guide`에는 `days` 배열을 둔다. 일곱 항목의 `id`는 `day-1`부터 `day-7`까지 중복 없이 지정한다. 각 날의 `title`, `focus`, `reflection`, `practice`는 직접 편집한 한국어 설명이며 `question`, `passage`, 선택적인 `experience`는 공개 문서의 경로다. 이 연결도 역참조에 반영된다. 날짜별 본문은 같은 내용을 Markdown과 메타데이터에 중복 작성하지 않고 사이트가 `days`를 표시한다.

이 사이트가 구성한 경로를 저자의 공식 프로그램이나 책 요약으로 표시하지 않는다. 공개 문답이나 설치 책의 자료를 참고했다면 확인 범위를 분리한다. 선택한 날의 공유 주소와 브라우저에 저장되는 읽음 표시를 구별한다. 읽은 날은 신앙이나 성장의 평가가 아니다.

## 9. 문서별 공개 산출물

전체 문서와 기존 검사용 API는 `compileBundle`에서 유지한다. 브라우저의 시작 데이터는 `src/generated/manifest.json`의 요약과 이전 주소 맵이다. `compilePublication`은 전체 문서와 검색 인덱스를 SHA-256 파일명으로 `public/generated-content/`에 만든다. 이 디렉터리는 Git에서 제외하며 빌드마다 위키로 재생성한다. 수집·LLM·외부 서비스 호출은 빌드에 포함하지 않는다.

본문 로더는 문서 자체와 필요한 체험·읽기 경로의 관계 문서를 함께 확인한 뒤 표시한다. 성공한 응답은 재사용하고, 실패하거나 필요한 필드가 없는 응답은 캐시에서 지워 재시도를 허용한다. 공유 주소의 체험 상태·날짜는 요약에서 확인하므로 본문을 기다리는 동안에도 유지된다. 검색에는 본문과 모든 표시되는 체험·읽기 안내의 설명을 포함한다.

생성기 정리는 자체 표시 파일이 있는 디렉터리에만 적용한다. 표시가 없는 기존 파일을 지우지 않는다. 한 페이지가 다른 페이지로 이동한 뒤 도착한 응답은 현재 화면에 반영하지 않는다. 네트워크 검사는 홈의 본문·검색 요청 0건, 검색 인덱스의 재사용, 상태 변경 후 본문 재요청 0건, 실패·잘못된 응답·연결 복구·빠른 화면 전환을 확인한다.


## 10. 읽던 자리에서 개념 이해하기

질문의 실제 문장에서 낯선 개념을 사용하면, 의미가 맞는 첫 위치에 기존 Concept 문서 링크를 명시적으로 연결한다. 같은 단어가 나올 때마다 링크를 반복하거나 본문과 관계없는 용어를 붙이지 않는다. Markdown 원본의 링크는 일반 OKF 소비자에서도 전체 개념 문서로 읽을 수 있다.

사이트에서 생성한 개념 링크에는 설명 창을 여는 의미를 표시한다. 보통 클릭은 현재 주소·체험 상태·읽기 날짜를 유지하면서 말뜻을 보여 주고, 수정 키 클릭은 원래 링크대로 새 탭을 연다. 상세 문서는 요청 시에만 불러오며 기존 성공 캐시와 실패 재시도 정책을 따른다. 이전 요청이 늦게 끝나도 다른 개념이나 닫힌 창을 다시 표시하지 않는다.

설명 창은 네이티브 dialog를 사용한다. 닫기와 Escape, 원래 링크로의 초점 복귀, 키보드 이동과 모바일 내부 스크롤을 브라우저에서 확인한다. 본문 HTML은 동일한 내용일 때 다시 쓰지 않아 원래 링크 DOM을 보존한다. 창 안의 근거 각주는 공개 페이지의 주소를 바꾸지 않고 해당 출처를 펼치며, 원자료는 새 탭에서 이어 읽는다. 설명 전체로 이동할 때는 기존 페이지 이동과 뒤로 가기를 사용한다.


브라우저·컴포넌트 검사에서는 로딩 안내에도 문서 제목이 표시됨을 고려한다. 제목만 기다리지 말고 실제 `.reading-body`나 체험·출처가 준비된 뒤 본문을 확인한다. 체험의 안내·선택한 상태·근거 설명에 같은 표현이 반복될 수 있으므로, 검사할 패널이나 역할을 먼저 좁혀 선택한다.


## 11. 질문 중심 읽기 지도

읽기 지도는 공개 Question 문서의 `links`와 공개 요약 목록을 사용한다. 본문·자료 원문이나 검색 인덱스를 미리 불러오지 않는다. 내부 위키 ID는 `documentById`로 찾고, 주소의 `public_id`와 혼동하지 않는다. 파일 슬러그가 같아도 문서 종류와 공개 ID는 다를 수 있다.

선은 해당 질문에서 함께 읽도록 편집한 자료 연결이다. 성경 본문 사이의 직접 인용·약속과 성취·주제 관계를 입증하는 선으로 표시하지 않는다. 그 관계의 이유와 근거는 해당 본문·연결 해설에서 확인한다. 지도는 중복 연결을 제거하고 본문·용어·출처·체험·다른 질문·이어 읽기로 자료를 나눈다.

`?view=map&focus=sin-question&group=concepts&node=sin`처럼 질문·종류·자료를 공유한다. 질문은 공개 Question만 허용하고, 선택한 자료는 해당 질문의 현재 필터에 실제로 연결되어 있어야 한다. 잘못된 값은 안내와 함께 복구하고 공유에는 복구한 선택을 사용한다. 기존 `doc`·본문·경로 주소의 우선순위를 보존한다.

데스크톱 지도는 세 열, 휴대폰은 한 열로 그린다. 연결 선을 모든 자료 카드보다 먼저 그려 글을 가리지 않는다. 긴 제목의 전체 이름은 키보드 접근 이름과 글 목록에 보존한다. Enter·Space 선택, 설명 창의 초점 복귀, 전체 페이지 이동과 복원, 상세 요청 0건을 브라우저에서 확인한다.

## 12. 본문 관계의 근거와 해석

`relationship.kind`는 직접 연결·약속과 성취의 해석·주제의 연결·삶의 적용을 나타낸다. 검토한 관계는 선택적으로 `basis`와 `basisExplanation`을 함께 둔다. `explicit`은 본문에 명시된 선언이나 인용, `allusion`은 반복되는 표현과 문맥의 암시, `editorial`은 함께 읽는 편집 해석이다. 이 분류는 해석의 옳고 그름이나 중요도를 평가하는 점수가 아니다.

두 필드는 짝으로 사용하며 설명은 실제 단서를 구체적으로 밝혀야 한다. 명시적 선언을 구약의 직접 인용으로 오인하게 쓰지 않는다. 보충 본문의 직접 인용과 원래 관계의 양 끝점에 있는 인용을 구별한다. 근거는 관계 전체를 증명하는 만능 링크 대신 실제 읽은 장·절 URL과 범위로 기록한다. 영어 번역을 대조했으면 번역과 언어를 공개한다.

선택한 관계의 근거 설명은 상세 문서를 불러온 뒤 표시한다. 시작 요약 데이터에 해석 문장을 중복 싣지 않는다. 이번 7관계 외의 기존 관계에 새 근거 분류를 자동으로 붙이지 않는다. 관련 본문에서 먼저 관찰할 내용은 그 본문 자체의 문맥으로 쓰고, 다른 본문과의 해석은 별도 단락으로 설명한다. 검토 기록에는 실제 검토 범위를 밝혀 문서의 모든 고백·주장을 재검증한 것으로 확대하지 않는다.

## 13. 성경 읽기 경로의 관계 선택

성경 읽기 경로의 지도는 해당 OKF 문서의 `node_ids`와 `connection_ids`를 사용한다. 질문 중심 지도에서 함께 읽도록 연결한 자료들과 구별한다. 성경 관계의 종류와 이유는 기존 관계 문서의 설명과 근거를 그대로 읽는다.

`?doc=path-covenant&relation=relation-covenant-new-table`처럼 경로와 관계의 공개 ID를 공유한다. 관계 선택은 해당 경로의 연결 목록에 속하고 양 끝점도 그 경로의 본문 목록에 있을 때만 허용한다. 일반 페이지·없는 관계·다른 경로의 관계는 안내와 함께 선택을 해제한다. 검사에는 시작 요약의 실제 연결 목록과 끝점을 사용하므로 주소 검증을 위해 본문을 추가 요청하지 않는다. 공유는 복구된 선택으로 만들고 기존 문서·본문·레거시 경로·체험 상태·읽을 날 주소를 유지한다.

상세 경로의 본문 목록과 관계 목록이 시작 요약과 다르면 불완전한 화면을 표시하지 않고 로딩 오류·재시도를 제공한다. 선택 변경은 주소만 갱신하며 같은 경로의 상세 자료를 다시 요청하지 않는다. 본문이나 연결 해설을 읽고 뒤로 돌아오면 주소의 관계를 다시 표시한다. 관계 문서의 `public_id`와 파일 경로·구절 슬러그를 혼동하지 않는다.

지도는 선을 먼저 그리고 본문 이름을 그 위에 표시한다. 휴대폰에서는 한 열로 구성하고, 실제 지도 영역의 폭에 맞춰 글자를 읽을 수 있게 한다. 본문 노드는 전체 장절과 이름을 가진 실제 링크로 제공하고 수정 키 클릭의 기본 동작을 보존한다. 관계를 선택하면 그 양 끝점과 근거를 함께 표시한다. 글 목록에서도 모든 본문과 관계를 읽고 선택할 수 있어야 하며, 목록 전환과 관계 선택은 상세 자료를 추가로 불러오지 않는다.
