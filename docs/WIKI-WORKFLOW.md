# 지식 위키 작업 흐름

이 저장소의 `wiki/` Markdown이 콘텐츠 원본이다. 출판 사이트는 이를 빌드해 정적 JSON으로 만들기 때문에 자료를 편집할 때 생성 파일을 직접 수정하지 않는다. 작업은 질문이나 개념에 필요한 출처를 좁혀 확인하고, 필요한 문서만 갱신한 뒤 인덱스와 검사를 업데이트하는 순서로 한다.

## 1. 기존 지식부터 찾기

먼저 `wiki/index.md`와 해당 분류의 `index.md`를 읽고 관련 문서를 따라간다. 질문 문서는 연결된 성경 본문, 본문 관계, 개념, 참고 자료를 출발점으로 삼는다. 이미 확인한 출처와 요약이 있으면 그대로 활용하고, 필요한 공백이 있을 때만 새 조사를 한다. 전체 위키를 다시 읽거나 모든 출처를 반복 수집하지 않는다.

## 2. 출처 수집과 확인

새 웹 자료는 수집 명령으로 참고 문서 초안을 만들 수 있다.

```bash
npm run wiki:ingest -- --url https://example.org/article --id source-slug --title "자료 제목" --related questions/acceptance,concepts/grace
```

`--related` 값은 `wiki/`에 있는 문서의 bundle-relative 경로이며 쉼표로 구분한다. 수집기는 `raw/ingest-catalog.json`에 URL, 확인 시각, 접근 상태, 해시와 관련 문서를 기록한다. 접근 가능한 원자료의 바이트는 `raw/snapshots/<sha256>`에 저장하지만, `raw/snapshots/`는 `.gitignore` 대상이어서 Git에 추가되지 않는다. 기존에 편집된 출처 조사 메타데이터는 `raw/source-catalog.json`에서 관리한다. 저작물 원문, 설교 전사, 긴 인용을 위키나 카탈로그에 옮기지 않는다.

수집은 초안 작성이지 원자료 검토를 대신하지 않는다. 원문을 직접 읽을 수 있으면 제목·저자·본문 범위를 확인하고 자신의 말로 요약한다. 페이지 개요, 카탈로그 항목, 검색 결과 일부, 원문 전체 확인은 분명히 구별한다. 접근이 막혔으면 그 상태를 그대로 기록하고, 간접 단서로 저자의 상세 주장을 만들지 않는다. 원문 전문과 검색 결과의 해시가 달라졌다면 해당 출처와 연결 문서만 재확인한다. 원문을 읽지 않은 사람을 저자나 검토자로 표시하지 않는다.

## 3. 읽을 수 있는 문서로 편집

일반 문서의 경로와 ID는 `wiki/<분류>/<slug>.md` 및 bundle-relative `분류/slug`다. 사이트 주소에서 쓰는 `public_id`는 별도 식별자이므로 파일을 옮겨도 안정적으로 유지한다. 문서에는 `type`, `title`, `description`, `public_id`, `status`, `published`, `tags`, `sources`, `generated`를 둔다. 출처마다 고유한 `sources[].id`, 원자료 `resource`, 제목을 기록하고, 생성 기록에는 실제 작업자·프로세스와 ISO 8601 시각을 쓴다. 사람 이름을 작성자나 검토자로 꾸며 쓰지 않는다.

공개 문서 본문은 한국어 prose로 작성하고, 인용 키는 같은 문서의 `sources[].id`와 일치시킨다. 문서 간 Markdown 링크는 번들 루트 기준 `/concepts/grace.md` 또는 문서 상대 경로를 사용하고, 질문 문서의 본문·경험 연결과 관계 문서의 양 끝점은 실제 공개 문서를 가리켜야 한다. 필요한 비교나 종합은 해당 질문의 본문에 근거를 밝혀 직접 작성한다. 질문 페이지가 요구하는 필수 섹션과 문서 유형별 메타데이터는 기존 동종 문서를 참고한다.

일반 Markdown·OKF 소비자는 의미가 통하는 제목과 단락, 내부 링크, YAML frontmatter를 읽으면 된다. 프로젝트의 추가 검사는 안정적인 공개 문서에 출처 ID, 유효한 사이트 링크, 학습 데이터 구조 등이 있는지 확인한다. `status: draft`와 `published: false`인 초안은 공개 사이트 번들에 실리지 않는다. `verified`는 실제 수행한 내용·출처 대조의 주체와 시각을 기록한다. 구조 검사와 내용 검토를 구별하고, 사람이 직접 검토했을 때만 `human:` 주체로 표시한다. 의미 있는 내용 수정 뒤에는 기존 검토를 로그로 옮기고 현재 개정본을 다시 검토한다.

## 4. 인덱스와 갱신 기록

문서 제목·링크·설명을 바꾼 뒤에는 다음 명령으로 위키 인덱스를 다시 만든다. 명령 뒤 문장은 날짜별 갱신 기록에 추가된다.

```bash
npm run wiki:sync -- "복음과 은혜 개념의 설명 및 연결 질문을 갱신했다."
```

`wiki/log.md`는 새 기록을 위에 쌓으므로 날짜 순서를 확인한다. 출처를 조사한 경우 기록에는 실제 읽은 범위와 관련 문서를 간단히 남긴다. 변하지 않은 자료는 다시 다운로드하거나 요약하지 않는다.

## 5. 검사 및 배포

```bash
npm run content:check
npm test
npm run build
```

`content:check`는 출판 문서의 YAML과 ID, 인용 키, 링크, 질문·본문·관계·학습 경험의 프로젝트 규칙을 검사한다. 테스트와 빌드는 앱 데이터와 사용자 흐름을 확인한다. `npm run check`는 세 검사를 묶어 실행하며 GitHub Actions도 이 검사를 통과해야 GitHub Pages에 배포한다. `src/generated/content.json`은 로컬 빌드 산출물이므로 커밋하지 않는다.

## 6. 질문에서 지식을 축적하고 위키를 점검하기

자료에 대한 질문을 받으면 인덱스에서 관련 문서를 좁혀 읽고, 원자료를 대조하면서 인용을 포함한 답을 만든다. 재사용할 만한 비교·종합을 위키에 남기도록 요청받았다면 일반 OKF 초안을 작성하고 관련 문서에 링크한다. 문서 간 다른 견해를 조용히 덮어쓰지 말고 출처와 차이를 함께 설명한다.

`npm run wiki:lint`는 공개 개념·참고자료의 들어오는 연결, `stale_after`가 있는 자료의 재확인 기한, 조사 대기 문서를 점검한다. 오래된 교리라는 이유만으로 성경 해석에 임의의 만료일을 붙이지 않는다. 연결 공백과 기한은 도구로 찾고, 모순·과도한 일반화·저자별 견해 차이는 관련 원자료를 읽어 점검한다. 필요한 수정 후 인덱스와 로그를 갱신한다.

`npm run test:browser`는 배포용 빌드를 만든 뒤 데스크톱과 모바일 Chromium에서 실제 조작을 확인한다. CI는 이미 빌드한 결과에 브라우저 검사를 수행하고, 모든 검사가 성공해야 배포한다.
